# Tab lock and record

- `9-1` A browser, for this specification, is the set of pages that share `localStorage` and locks, such as the windows of one browser profile.
- `9-2` Before creating, joining or returning, a page takes the lock of the app ID in its browser without waiting. When another page holds the lock, or the browser does not give it for another reason, creating, joining or returning fails with "open elsewhere" before it starts, and the record stays as it is. The page then does nothing more about it: it does not wait for the lock and does not go on when the lock is free. While a page holds the lock, a call to create, join or return on it fails ([1-14](1-room.md)).
- `9-3` A page holds the lock until creating, joining or returning fails, the room ends for it, the app leaves or the page closes. A page whose scripts the browser suspended holds it. When a page goes into the back/forward cache, it lets the lock go, and when it comes back from there, it reloads. A page starts anew when it loads, such as after a reload or after it comes back from the back/forward cache, and it then keeps nothing in memory from before.
- `9-4` A browser keeps at most one record for each app ID, in `localStorage`. The record keeps the code, the token, the number, the waiting time and the record data (9-7), what [5-5](5-owner-return.md) lists on the owner's page, and since when the owner is lost on a participant's page ([3-3](3-participant.md), [3-9](3-participant.md)). A page writes the record when the room is created or the join completes, and again each time what it keeps changes, each time as a whole. When a write fails, the page goes on with what it keeps in memory, and a page that starts anew (9-3) starts from the record last written. A record that cannot be read or that is not in the form that the rooms module writes counts as no record.
- `9-5` The app returns with an app ID to go back to the room of its record. After taking the lock, the page creates, joins or returns as this table says. "Leaves it" means 9-6.
  | Record | Create | Join with the record's code | Join with another code | Return |
  | --- | --- | --- | --- | --- |
  | none | creates ([4-2](4-owner.md)) | — | joins ([2-3](2-join.md)) | fails with "no room" |
  | a participant's token | leaves it and creates | returns ([3-9](3-participant.md)) | leaves it and joins | returns ([3-9](3-participant.md)) |
  | the owner's token | leaves it and creates | returns ([5-1](5-owner-return.md)) | leaves it and joins | returns ([5-1](5-owner-return.md)) |
- `9-6` To leave the room of the record before creating or joining, the page opens a signaling connection, sends the leave with the token of the record ([10-8](10-server-room.md)), deletes the record and goes on creating or joining over the same connection. When the signaling connection cannot open ([1-13](1-room.md)), creating or joining fails with "offline", and the record stays.
- `9-7` Record data is a JSON value that the app gives the rooms module to keep in the record. The rooms module sets no limit on its size; a write that the browser refuses, such as over its storage limit, is a write that fails (9-4). When the app gives record data while the record exists, the page writes the record before the call returns. Before the page first writes the record, it keeps the record data and writes it then. When the value is not JSON, the call fails ([1-14](1-room.md)).
- `9-8` When joining or returning goes on as a return from the record (9-5), the app is told at once, before the page opens a signaling connection, that the page returns as the owner or as a participant, with the number and the record data that the record keeps.
