# Workflow

These rules say how to work on any change. [workflow-specs.md](/docs/conventions/workflow-specs.md) adds how specifications and code change, and [workflow-checks.md](/docs/conventions/workflow-checks.md) says what to check along the way.

## Starting

Before starting work, read the [writing rules](/docs/conventions/writing.md) and the conventions files that cover what the task changes, as the [map](/AGENTS.md) lists them, and follow them.

Read every `AGENTS.md` on the path of the files the task changes, and, following their maps and the maps they link to, the [documents](/docs/glossary.md#document) the task needs. Keep changes within the task's [agreed points](#decisions) and what the Decisions section lets you decide.

Files that git ignores, such as `node_modules` and build output, are not part of the repository. Do not edit them or take them as rules.

Before starting, check [open questions](/docs/open-questions.md) about the [projects](/docs/glossary.md#project), [modules](/docs/glossary.md#module) or topics the task touches and raise them with the user. Add a question only with the user's agreement. When a question is decided, move the decision into the document it concerns, such as a conventions file, a document that an `AGENTS.md` links to, or a specification, and delete the question. The Decisions section below says when the decision also needs a [decision record](/docs/conventions/decisions.md).

## Cutting a task into pieces

Before changing any file, read every outline in `whenparty-notes/outlines/`. The `whenparty-notes` folder lies beside the repository's main working tree, which is the parent of the folder that `git rev-parse --path-format=absolute --git-common-dir` prints. When the folder or its `outlines/` is missing, there are no outlines; when the session may not read the folder, ask the user where the outlines are. When the task overlaps unfinished work in another outline, tell the user before cutting the task.

Then cut the task into pieces as small as is reasonable. Changes that cannot reach `main` one without the other, such as a rule and the documents that must follow it, are one piece, and so are small fixes of one kind, such as of a row's animation and of a button's colour. Each piece reaches `main` in a pull request of its own and leaves everything that already works on `main` working. Each piece comes after the pieces it relies on. Of the pieces that can go next, take first the smallest one that works end to end, from its user, a person or another project or module, through every project and module it needs; a test may stand in for the user. Split a piece too large to understand at once into smaller pieces that each work end to end, and only when no such split exists, by [project](/docs/glossary.md#project) or [module](/docs/glossary.md#module), starting with the one that the others call.

The outline of a task is a file in `whenparty-notes/outlines/` named after the task. It holds the [agreed points](#decisions) of the task, each followed by a line with its reason, taken from the question that the user said yes to or from the user's own words, and the [acceptance cases](#decisions) of the task. When the task has several pieces, it also holds the pieces in order, one line each on what it adds and what is still missing after it, then what more than one piece relies on, such as a type, a term or a rule. Write it when the user says yes to a point or the task has several pieces, creating the folder when it is missing, and delete it when the task is done or the user cancels it.

When the task has several pieces, the session that wrote the outline, or one that the user asks to continue it, leads the task; these rules call it the lead. For each piece, the lead starts a new Claude Code session or, when it cannot, gives the user a prompt for one; either gets the path to the outline and the piece's line. A piece does not run in a subagent, which can neither ask the user nor start the [reviewers](/docs/conventions/workflow-checks.md#documents). A piece's session takes its piece as the task and as the change that [workflow-specs.md](/docs/conventions/workflow-specs.md) speaks of, records the points that the user says yes to and the acceptance cases of its piece in the outline it got and writes no outline of its own: when the piece needs splitting or a rule change first, it stops and tells the lead. When the piece's pull request is merged, the lead checks the piece against the outline, tells the user of any difference, marks the piece done and, after reading the rules that the piece changed, starts the next piece from that `main`.

## Decisions

Agree with the user the functionality of a task, what the things it changes do and promise, and what the rules of work say: the [conventions files](/AGENTS.md#conventions-files), the root `AGENTS.md`, the [glossary](/docs/glossary.md) and what `.claude/` holds, as [.claude/AGENTS.md](/.claude/AGENTS.md) maps it. Agree them in a dialogue, one short question at a time, each asked as [Messages to the user and the lead](#messages-to-the-user-and-the-lead) says; small points may share a question. When there is much to agree, cut the task smaller. The agreed points of a task are what the user's request asks for and each point that the user says yes to; the task's [outline](#cutting-a-task-into-pieces) records them when there is one. You write the texts that carry the agreed points out, such as a behaviour model, a specification edit or a rule; do not ask the user to read them in full or to approve them apart from the change.

Decide by common sense everything else that no rule gives to the user, such as modules, packages, numbers, texts and what the agreed points leave open, what a reviewer's finding asks for included: behaviour in a case they do not cover, such as what a page does with a wrong room code, or a fix of a requirement that no agreed point states. Weigh the options and choose the best. A decision must serve the agreed points and harm neither them nor what already works; it need not be one without which they would not work. Stop and prepare the decision with the [`decide` skill](/.claude/skills/decide/SKILL.md) when the task would need to change, weaken or put off an agreed point, break what already works or change a rule of work beyond the agreed points, when another rule gives the decision to the user, or when rules contradict each other or make the task impossible. The user decides.

When the task has an outline, write its acceptance cases there before you write the solution: for each agreed point, at least one situation and what must happen in it, such as "a page opened with a wrong room code says that the room was not found". Add cases for what the agreed points leave open; they are decisions of yours. Ask the user only when you cannot write a case without choosing between two readings of an agreed point. You may change a case of your own and say why in your report; a case that restates an agreed point changes only with the point. Without an outline, the agreed points in the user's request stand in for the acceptance cases. The change must give every case its outcome, and [workflow-checks.md](/docs/conventions/workflow-checks.md) says who checks that.

Propose or choose an option that a [decision record](/docs/conventions/decisions.md) rejected only when facts absent from that record affect the choice, and link the record and name those facts. When an option would change, weaken or put off an agreed point of the current task or change a rule of work beyond the agreed points, the task can proceed without it, and it looks better than the option you would choose by common sense, give a new subagent, which has not seen the discussion, both options and the reason behind each agreed point or rule the option would change, and ask whether the option is substantially better. Take the reason for an agreed point from the outline or the user's request, and for a rule of work from its own text, the decision records about it and the commit messages and pull request descriptions that made it, where the [writing rules](/docs/conventions/writing.md) put reasons. If a reason is unavailable, say so rather than inventing it. When the subagent finds the option substantially better, stop and prepare it for the user with the `decide` skill; otherwise leave it out.

Within the limits above, you may revise earlier decisions by common sense, whoever made them, including requirements, decisions recorded in decision records and the agreed points of finished tasks. Replacing behaviour that works with other behaviour that, by good practice, is no worse for the people who use it does not harm what already works.

Save at once each correction that the user makes to your work as an entry of your memory that records its case, and apply it to that case. When a question or correction of the user shows that the two of you understood something differently, also add it to `whenparty-notes/weekly-review/mismatches.md`, with the date, the user's words and what was understood differently, for the weekly pass that the [`docs-weekly` skill](/.claude/skills/docs-weekly/SKILL.md) describes. Take a lesson for other cases only from an answer in which the user says that they are sure and has not said that they are tired, and save it in your memory. When the user says that you propose too much, reconsider how you cut the task and put your questions, and propose a change of these rules when they cause it.

The user has the final word, even when it contradicts these rules. When it does, remind the user of the rule, then follow their decision.

After any decision under this section, yours or the user's, or on an open question, write a decision record when the decision record rules call for one; after a decision of the user, tell the user whether the rules call for one and why. The record reaches `main` with the first change that follows from it, or on its own when the decision changes nothing. A change that goes against a decision record rewrites or deletes the record in the same change, as the decision record rules describe. A change that moves or renames something linked under the record's Consequences updates the link.

## Messages to the user and the lead

Write every message to the user, and every message that a piece's session gives the [lead](#cutting-a-task-into-pieces), for a reader who has seen the agreed points but not the changed files, a subagent's report or Codex's answer, and who does not keep your earlier messages in view. Name each finding and each option by what it is, not by a number, count or label from a report, an answer or an earlier message, such as "point 5", "9 of 11" or "the first option". Do not retell how the reviews and Codex went, and say that you checked only what you checked. When a skill asks you to report findings, present them as this section says, and name each of them only when the user asked for that review.

- Describe each change in plain words, using a concrete case to show what people or agents now see or do, such as what a page does with a wrong room code. Do not present the changed text or a translation that follows it sentence by sentence.
- Ask each question under [Decisions](#decisions), including one prepared by the `decide` skill, with the reason the decision is needed and a concrete case where it matters. When you offer options, first state how many there are and whether the user must choose one or may combine them. Describe what you propose, or each option when you offer several, by what people or agents would see or do in that case, what it fixes and its advantages and drawbacks; then say what you recommend and why. List under the question the smaller points that came up with it and that Decisions leaves to you, and say that you will settle them.
- In the report in which you show the user a change for the approval that [Pull requests](#pull-requests) asks for, start with a short list of what is now different. Include each agreed point that the change carries out, each of your own decisions about how the result behaves or what a rule requires, and each earlier decision that you revised, whoever made it. Mark your decisions as yours and give their reasons. Group changes that carry out one decision in its item, and put the fixes that only [reword](/docs/conventions/workflow-checks.md#ending-a-review) in one item, in plain words. For code, say what it does, not how it is built. Then, in a sentence or two, name the findings of a [reviewer](/docs/conventions/workflow-checks.md#documents) or of [`last-reader`](/docs/conventions/workflow-checks.md#last-reading) that you rejected or [`findings-verifier`](/docs/conventions/workflow-checks.md#ending-a-review) refuted, when their fixes would [change the meaning](/docs/conventions/workflow-checks.md#ending-a-review) and they are not [outside the change](/docs/conventions/workflow-checks.md#review-findings), and say why. Do the same for advice of Codex that you did not take, when taking it would change the meaning. Say what you checked and could not check, list the findings outside the change and the suggestions that the review left out as work for a later task, and name the fixes that change the meaning and that no reviewer has read since you made them. Name the changed files in one sentence. End with what comes next or is not done yet.
- Any other message during the work keeps the order and the rules of that report for what is new since your last message, and leaves out the fixes that only reword and the other parts with nothing new. It ends with its question, if it has one, then what comes next or is not done yet.

## Pull requests

Commit a change, push it and open its pull request only after you show it to the user and the user approves it, and merge it only when the user agrees to merge it.
