# Writing

These rules apply to every [document](/docs/glossary.md#document), and to responses where they say so. The other conventions files that the [map](/AGENTS.md) lists add rules for the kinds of files they cover, such as the [folder document rules](/docs/conventions/folder-docs.md), and [link-paths.md](/docs/conventions/link-paths.md) says how a link writes its path.

- Use the minimum text needed in documents and responses.
- Describe only current behaviour. Replace or delete superseded text without adding change histories or before-and-after narratives. Keep history in Git. Reasons for a change belong in commit messages and in the pull request description when there is one. The [specification rules](/docs/conventions/specs.md) say how a specification and `docs/PLANNED.md` describe changes that are not on `main` yet.
- Only [decision records](/docs/conventions/decisions.md) weigh a choice against the options it rejected and describe the decision it replaced. Other documents may state the fact a rule depends on.
- Describe each rule in one place.
- A document relies on another document when its text applies a rule or uses or retells a fact that the other states, or uses a term that the other defines, such as a term of the [glossary](/docs/glossary.md). Following the rules of the conventions files that cover a document is not relying on them. At the first use of what it takes from a section of another document, the relying document links to the heading of the innermost section that holds it, or to the whole document when no one section does; it may link again at later uses. When several documents state the fact, it links to the one where the fact goes, as [Where knowledge goes](/docs/conventions/folder-docs.md#where-knowledge-goes) says. A document need not link to the documents that rely on it: a search for its file name, keeping the matches whose link leads to it, finds them. Between requirements of specifications, the [specification rules](/docs/conventions/specs.md#content) say instead when one relies on another and how it refers to it.
- A fact that only code or a config states needs no link to a document and may link to that file. No document links to a README as the source of what it uses, because a README is wrong when it differs, as the [README rules](/docs/conventions/folder-docs.md#readmemd) say; only a README links to a README, to point the reader to the README of a folder it names. The front matter of a skill or subagent, its description included, has no links, and the text below it links at its own first use.
- Text uses a glossary term, and links it to the term's heading, only where it uses the term in the glossary's sense. The name of a part, such as "rooms module" or "signaling deployment", is not a use of the glossary term in it, except in a sentence that says what the part is. Outside the part's own documents, a link on its name leads to its `AGENTS.md`, or to the `AGENTS.md` whose map names it when it has none; in a README, it may lead to the part's README.
- When one or a few requirements hold what a document outside a specification uses, it names them by ID and a link to their file, with the name of their project or module when another specification has a file of that name, such as "`2-2` of [2-headers.md](/infra/docs/specs/2-headers.md)" or "`2-3` of tictactoe's [2-page.md](/games/titles/tictactoe/docs/specs/2-page.md)". A later ID of the same file in the same paragraph, list item or table cell may stand alone.
- Give each document one purpose and one area it applies to, such as one kind of file, one [project](/docs/glossary.md#project) or one [module](/docs/glossary.md#module).
- Name a document after its purpose and area. When a split or a new document needs a name, check two names: after a split, whether the old name still fits the document that keeps it; and whether a document in the same folder already has the name that fits the new one best. Rename that document when another name describes it better; if you do not rename it, give the new document another name. A rename updates every link and path to the document in the same change, code included.
- When part of a document has another purpose or area, make it a topic of its own: a title that states its purpose, text that reads without the rest of the document, and links to related rules. Move it to the document with that purpose and area, or to a new one when no document has it, and link to it from where it was. A part can be a whole section or a few paragraphs of one.
- Add documents only when existing references cannot supply the context needed for the task. Describe behaviour and contracts without retelling code.
- In a README or a specification, show states and transitions, flows with branches and how parts connect as a diagram where that is shorter or clearer than sentences or lists. Draw it as Mermaid code in a `mermaid` code block, not as an image file or a drawing in plain text, and keep its labels to a few words. Other documents, such as an `AGENTS.md`, the files in a `docs/` folder other than a specification, and decision records, have no diagrams. A file tree is not a diagram and stays plain text in any document.
- In any document, show items that share the same fields as a table where that is shorter or clearer than sentences or lists. The text around a diagram or table adds only what it cannot show, such as links for what the labels of a diagram take from other documents.
- Write for a reader who knows the repository documentation but not the discussions behind it. Do not refer to conversations or agreements. Define a term that can be read in more than one way in the [glossary](/docs/glossary.md).
