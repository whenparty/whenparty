# Workflow: checks

These rules say what to check while working on a change that the workflow files, [workflow.md](/docs/conventions/workflow.md) and [workflow-specs.md](/docs/conventions/workflow-specs.md), describe. Repeat successful checks only after relevant changes or new evidence of a problem. Report what was actually verified.

## Documents

- Before editing a [document](/docs/glossary.md#document), besides what the [workflow](/docs/conventions/workflow.md#starting) says to read, search with `git grep -i --untracked` for the names, terms and paths that the old and the new text use, including what the edit removes, and read every document that has a match. Resolve the duplicates and contradictions the edit would create.
- Before proposing the text of a document that goes into the repository, give it to the [`docs-reviewer` subagent](/.claude/agents/docs-reviewer.md) with the files it goes into and links to. Give a behaviour model that [workflow-specs.md](/docs/conventions/workflow-specs.md#behaviour-changes) calls for to the [`behaviour-reviewer` subagent](/.claude/agents/behaviour-reviewer.md) with the sources of the change, such as the user's requirements and, for a piece of an [outline](/docs/conventions/workflow.md#cutting-a-task-into-pieces), the outline with the piece named. Give a specification edit that changes behaviour also to `behaviour-reviewer`, with its model, against which it checks the edit, or with the sources of the change when it has no model, and with its state tables when the [testing rules](/docs/conventions/tests.md) require them. Start a new run of a reviewer for each review, not one that has seen an earlier version or the discussion. Name the files and say in a sentence what changed; do not ask a reviewer to skip any of its checks. The reviewers only suggest changes. Weigh each suggestion and report your conclusions, including the suggestions you rejected.
- When an agent breaks a rule that a document states, first check whether the rule is unclear, stated in several places or in a document that mixes purposes, as the [writing rules](/docs/conventions/writing.md) describe. Fix that before adding emphasis or another rule.
- After adding a document or changing a rule, have the `docs-reviewer` subagent read every [document](/docs/glossary.md#document) that git tracks or the change adds. Fix the places it reports.

## Code

- During implementation, run the typechecks and the tests that run in Node of the packages the change touches, as the [testing rules](/docs/conventions/tests.md) tell them from the tests that run in a browser.
- Before reporting a change as done, run them also for the packages that depend on those, and run the browser tests of the affected requirements, as the next bullet defines them. The [documents on how to work](/docs/conventions/folder-docs.md#agentsmd) in the [project](/docs/glossary.md#project) that holds the packages give the commands, and [checks.md](/.github/docs/checks.md) says which browser tests CI runs.
- Before reporting a change as done, check each affected requirement against the code and its tests. Affected requirements are those the branch changes in `docs/specs/` since it left `main`, those that link to a specification file the branch changes, and, for the innermost project or [module](/docs/glossary.md#module) whose code includes a changed file, those of its own [specification](/docs/conventions/specs.md) that the changed code carries out and those of other specifications that link to a file of it. `git grep -i --untracked` in `*/docs/specs/*` finds the requirements that link there by the name of each changed specification file and of each folder of each such project or module; keep the matches whose link leads there.
