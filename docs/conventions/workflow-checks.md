# Workflow: checks

These rules say what to check while working on a change that the workflow files, [workflow.md](/docs/conventions/workflow.md) and [workflow-specs.md](/docs/conventions/workflow-specs.md), describe. They also say how the findings of a review are classed, how a review ends, when to ask Codex, and how a change and its report are read once more before the user sees them. [How to use these files](/docs/conventions/workflow.md#how-to-use-these-files) says how an agent uses all three workflow files.

## Documents

- Before editing a [document](/docs/glossary.md#document), besides what the [workflow](/docs/conventions/workflow.md#starting) says to read, search with `git grep -i --untracked` for the names, terms and paths that the old and the new text use, including what the edit removes, and read every document that has a match. Also read the documents that link to the edited document or give its path: search for its file name and keep the matches whose link or path leads to it, as the [writing rules](/docs/conventions/writing.md) say for links. A link to a heading counts only when the edit changes that heading or the section under it. Resolve the duplicates and contradictions the edit would create.
- Before the [last reading](#last-reading) of a change that adds or edits a document, give the change, such as `git diff $(git merge-base main HEAD)` and its untracked files, to the [`docs-reviewer` subagent](/.claude/agents/docs-reviewer.md), which reads in full each document that the change adds or edits and whatever else it needs. Give a behaviour model that [workflow-specs.md](/docs/conventions/workflow-specs.md#behaviour-changes) calls for to the [`behaviour-reviewer` subagent](/.claude/agents/behaviour-reviewer.md). Give a specification edit that changes behaviour also to `behaviour-reviewer`, with its model, when it has one, against which it checks the edit, and with its state tables when the [testing rules](/docs/conventions/tests.md) require them. Give every reviewer the sources of the change, such as the [agreed points](/docs/conventions/workflow.md#decisions) in the user's request and the task's [outline](/docs/conventions/workflow.md#cutting-a-task-into-pieces), with the piece named when the task has several, and list for it every decision of the change, the user's and yours, and how each was made; do not ask it to skip any of its checks. Each run of a reviewer is a new one, not one that has seen an earlier version or the discussion. The reviewers, `docs-reviewer` and `behaviour-reviewer`, only suggest changes. [Ending a review](#ending-a-review) says what to do with what they report, and [Messages to the user and the lead](/docs/conventions/workflow.md#messages-to-the-user-and-the-lead) says which of it your report names.
- When an agent breaks a rule that a document states, first check whether the rule is unclear, stated in several places or in a document that mixes purposes, as the [writing rules](/docs/conventions/writing.md) describe. Fix that before adding emphasis or another rule; for a document that mixes purposes, note the part for the weekly pass, as the writing rules say.
- When a change adds a document or changes a rule, such as a requirement, or the definition of a term, the same run of `docs-reviewer` also reads the documents that the change can affect. Find these documents without asking the user, even when they are every document of the repository, and name them to the reviewer:
  - for each document that the change adds, edits or deletes, the documents directly in its folder and directly in each folder above it up to the root, and those that link to it or give its path, found as the first bullet of this section says;
  - for a rule that the change adds, or changes so that a document that followed it may now break it, every document whose text the rule constrains, or, when a `git grep -i --untracked` search matches every text that can break the rule, such as a search for a word that the rule forbids, only the lines it matches, with their files and line numbers.

### Review findings

A finding must name the source of the change, rule, fact or required review check behind it and show the concrete error or unanswered case in the text. A suggestion without that evidence is not a finding, such as that a sentence with one right reading could be clearer; the reviewers list such suggestions after all findings, without a class. `docs-reviewer` and `behaviour-reviewer` give every finding one class and report findings in the class order below. Within each class, they report the most serious first.

- Breaks behaviour or a rule: the text gives behaviour that breaks a requirement, a scenario, a rule of its model or a source of the change under review, leaves out behaviour that they need, or adds behaviour that its model lacks; it states a wrong fact or contradicts another document; or it breaks a rule of the [conventions files](/AGENTS.md#conventions-files) in what it says or where it says it, such as a rule stated in two places or a link that the writing rules require and the text lacks.
- Wording only: the text has one reading, that reading is right, and the text stands in the right place; it breaks a rule of the conventions files only in how it says it, such as a sentence longer than the minimum text needs, a list where a table would be shorter, or a link that leads to the right target in a path form that [link-paths.md](/docs/conventions/link-paths.md) does not allow.
- Outside the change: all of these hold:
  - the sentence, heading, table row or diagram line with the problem, or the place where missing text belongs, is as it was where the branch left `main` and has not moved;
  - the change neither causes nor worsens the problem, and nothing it adds or edits uses a rule, fact or term that the text with the problem states or defines;
  - neither a source of the change nor a rule or scenario of its model needs the fix, and no repository rule requires it in this change.

A finding that the text can be read in more than one way takes "Breaks behaviour or a rule" when, in a situation that it names, two plausible readings lead to different outcomes, or when a reader cannot tell what to do. Otherwise it is a suggestion. A reading is plausible when a reader can hold it without ignoring the text around the sentence, and a reading whose plausibility is in doubt is plausible. Text that clearly allows more than one behaviour has one reading.

A finding that fits the class "Outside the change" takes it in place of the others. Any other finding that fits more than one class takes the first of them, and one that fits none takes "Breaks behaviour or a rule". A finding that asks whether a behaviour is intended takes the class it would have if the behaviour is not intended.

### Ending a review

This subsection says how each review that [Documents](#documents) requires ends: of a change to documents, which `docs-reviewer` and, for a specification edit that changes behaviour, `behaviour-reviewer` read in one review; and of a behaviour model. A run of a review is a run of each reviewer that the review requires, with what Documents says to give it. A fix made in a review starts no other review. Ask the user, not Codex, about each finding that the [Decisions section](/docs/conventions/workflow.md#decisions) of the workflow sends to the user.

A fix changes the meaning when it adds, removes or changes a rule, a requirement, a scenario, a state, an outcome, a fact or the definition of a term, moves one of them to another requirement, section or document, settles which of two readings holds, or makes the text rely on a document or section that it did not rely on, as the [writing rules](/docs/conventions/writing.md) define relying. Any other fix only rewords, such as adding a link to a section that the text already relies on.

Check every fix of a finding, in a review and after the [last reading](#last-reading), against the current [acceptance cases](/docs/conventions/workflow.md#decisions), revised only as the Decisions section permits, and make no fix after which a case has another outcome. When a finding that you fix shows a wrong outcome in a situation, add an acceptance case with that situation and the right outcome to the outline, when the task has one.

- When the first run gives a finding of the class "Breaks behaviour or a rule", give its findings, with what the reviewers got, to the [`findings-verifier` subagent](/.claude/agents/findings-verifier.md), which tests each finding against the text and confirms its class, changes it or refutes the finding. Otherwise, check yourself that each finding of the class "Outside the change" meets all its conditions.
- Leave the refuted findings, the findings of the class "Outside the change" and the suggestions out of the change. Fix each of the other findings in the way you choose, or reject it when you can say why it is wrong. When none of these fixes changes the meaning, make them, and the review ends.
- Otherwise, before you fix, ask [Codex](#codex) how it would fix the findings of the class "Breaks behaviour or a rule" together so that a second run finds no error, and whether the solution itself should change. Give it each of these findings with its reason and the fix you intend.
- Then write the fixes of these findings yourself, in one batch. A fix changes only what its finding needs, with the dependent text that keeps it consistent. When you take another solution from Codex, write it in place of the fixes that it replaces; it is part of the batch.
- Give the result to a second run: what the first run got, in its current state, the findings of the first run and what you did with each, and the files that the batch touched. In a second run, a reviewer reads the whole current result and reports only what the fixes that the caller names left open or caused, an error between two of them included. Test each finding of the second run yourself, as `findings-verifier` does, and fix those of the class "Breaks behaviour or a rule": when the error lies in an edit of the batch that neither a finding nor a solution taken from Codex needed, undo that edit, and otherwise make the smallest fix that removes the error, with the dependent text that keeps it consistent. No reviewer runs a third time in one review.
- Last, make the fixes of the findings of the class "Wording only" of both runs. No reviewer reads them.

## Code

- While working on a change and before reporting it as done, run the typechecks and the tests that run in Node of the packages the change touches, as the [testing rules](/docs/conventions/tests.md) tell them from the tests that run in a browser, and no other tests, typechecks or builds apart from the runs that the next two bullets give. The [documents on how to work](/docs/conventions/folder-docs.md#agentsmd) in the [project](/docs/glossary.md#project) that holds the packages give the commands. CI runs the rest, such as the tests of the packages that depend on them, the browser tests and the builds of images, on the pull request or before the deploy of `main`, as [checks.md](/.github/docs/checks.md) says. A check that CI does not run, such as the smoke test of the image of index in its [verification.md](/games/index/docs/verification.md), runs locally as its document says.
- Write each test, such as one in Node, in a browser or in a shell script, before the code or the fix that it checks, and run it: it must fail at the check of its requirement or bug, not on a typo, an import or its setup. Then write the code and run it again: it must pass. A test of behaviour that already works and that the change does not touch, such as a missing test that a review asks for, runs once and passes. Run each test once after each later edit of it. Run a test that does not run in Node and that CI runs locally only in these runs, in one run with the other tests that need the same run at that point and in every browser in which CI runs it, and not again for other changes: CI runs it. A screenshot test of www, whose approved screenshots only CI makes, gets no run before the code, and its run after the code is in CI, as [tests.md](/www/docs/tests.md) says; when it fails there only by the differences that the change makes on purpose, update its approved screenshots as tests.md says, and that is no failure for the next bullet; [Pull requests](/docs/conventions/workflow.md#pull-requests) says that the user approves them before the merge.
- When a test fails in a run after the code, or in CI, on a pull request, in the merge queue or in a deploy of `main`, do not only make it pass. Find why it failed: a gap in the [specification](/docs/conventions/specs.md), code that does not do what a requirement says, or tests that are wrong or miss cases; a test that passes when run again failed for a cause too. Fix that cause: the specification, as [workflow-specs.md](/docs/conventions/workflow-specs.md) says, the code or the tests. Then run the tests that failed once more locally, a browser test in the browser in which it failed, and do this before you commit the fix of a failure in CI.
- Before reporting a change as done, check each affected requirement against the code and its tests. Affected requirements are those the branch changes in `docs/specs/` since it left `main`, those that link to a specification file the branch changes, and, for the innermost project or [module](/docs/glossary.md#module) whose code includes a changed file, those of its own [specification](/docs/conventions/specs.md) that the changed code carries out and those of other specifications that link to a file of it. `git grep -i --untracked` in `*/docs/specs/*` finds the requirements that link there by the name of each changed specification file and of each folder of each such project or module; keep the matches whose link leads there.
- After a check of this section passes, repeat it only after a change that can affect its result or new evidence of a problem.

## Codex

Codex is another model, and what it says is advice: you weigh it and write every text yourself. Call it with the [`codex` skill](/.claude/skills/codex/SKILL.md) in each of these cases, and otherwise only when the user asks for it:

- before the fixes of a review that lead to a second run, as [Ending a review](#ending-a-review) says;
- when the same failure remains after two attempts to fix it, such as a test that still fails or an animation that is still blurred;
- when, after weighing them as the [Decisions section](/docs/conventions/workflow.md#decisions) of the workflow says, you still cannot choose between two solutions or between two findings that contradict each other;
- in the weekly pass, to check that a changed text keeps its meaning, where the [`docs-weekly` skill](/.claude/skills/docs-weekly/SKILL.md) says.

Unless the user asks for it, ask Codex about a place or a question once; only the fixes before a second run may take to it a place that it has advised on.

Give it the whole task, not only the question: the sources of the change, for a specification edit its model and state tables, the changed files, the findings and what you and the user decided on each, and what you tried. It may read any other file. Ask your question, and ask it to say when the question is the wrong one and how it would then solve the whole task. Check what it proposes against the acceptance cases before you use it. When what it proposes would change, weaken or put off an agreed point, the Decisions section says when it goes to the user.

When Codex cannot run before the fixes of a review or for the check of the weekly pass that the `docs-weekly` skill names, do not replace it with another adviser and go no further: fix what keeps it from running, apart from the setup that the `codex` skill leaves to the user, or stop at once and give control back to the user. When the user asked for it, tell the user. In the other two cases, go on even where the skill says to stop: decide yourself, and say in your report that Codex could not run and what the user must set up.

## Last reading

Before you first show the user a change for the approval that [Pull requests](/docs/conventions/workflow.md#pull-requests) asks for, after the other checks of these rules, give it once to the [`last-reader` subagent](/.claude/agents/last-reader.md), which is not a reviewer. Give it every change since the branch left `main`, uncommitted and untracked files included, the sources of the change, with the piece named when the task has several, and the draft of your [report](/docs/conventions/workflow.md#messages-to-the-user-and-the-lead). Test each of its findings yourself, as `findings-verifier` does, fix what holds with the smallest fix that removes the error, and ask the user only about a finding that the Decisions section sends to the user. Fixes of its findings start no review and no second reading.

A correction that the user makes after the report gets no full review. Make it, revise the acceptance cases that it changes and, when it changes the meaning of a document, give the result to the reviewers as a [second run](#ending-a-review), with the correction in place of the findings of the first run.
