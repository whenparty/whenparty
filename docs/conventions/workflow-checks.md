# Workflow: checks

These rules say what to check while working on a change that the workflow files, [workflow.md](/docs/conventions/workflow.md) and [workflow-specs.md](/docs/conventions/workflow-specs.md), describe. They also say how the review subagents class and order their findings, how a review ends, and how Codex checks a change before the user sees it. Report what was actually verified.

## Documents

- Before editing a [document](/docs/glossary.md#document), besides what the [workflow](/docs/conventions/workflow.md#starting) says to read, search with `git grep -i --untracked` for the names, terms and paths that the old and the new text use, including what the edit removes, and read every document that has a match. Also read the documents that link to the edited document or give its path: search for its file name and keep the matches whose link or path leads to it, as the [writing rules](/docs/conventions/writing.md) say for links. A link to a heading counts only when the edit changes that heading or the section under it. Resolve the duplicates and contradictions the edit would create.
- Before the [Codex check](#codex-check) of a change that adds or edits a document, give the change, such as `git diff main` and its untracked files, to the [`docs-reviewer` subagent](/.claude/agents/docs-reviewer.md), which reads in full each document that the change adds or edits and whatever else it needs. Give a behaviour model that [workflow-specs.md](/docs/conventions/workflow-specs.md#behaviour-changes) calls for to the [`behaviour-reviewer` subagent](/.claude/agents/behaviour-reviewer.md) with the sources of the change, such as the [agreed points](/docs/conventions/workflow.md#decisions) in the user's request and the task's [outline](/docs/conventions/workflow.md#cutting-a-task-into-pieces), with the piece named when the task has several. Give a specification edit that changes behaviour also to `behaviour-reviewer`, with its model, against which it checks the edit, or with the sources of the change when it has no model, and with its state tables when the [testing rules](/docs/conventions/tests.md) require them. Each run of a reviewer is a new one, not one that has seen an earlier version or the discussion. List for a reviewer every decision of the change, the user's and yours, and how each was made; do not ask it to skip any of its checks. The reviewers only suggest changes. Weigh each suggestion and report your conclusions, including the suggestions you rejected.
- When an agent breaks a rule that a document states, first check whether the rule is unclear, stated in several places or in a document that mixes purposes, as the [writing rules](/docs/conventions/writing.md) describe. Fix that before adding emphasis or another rule.
- After adding a document or changing a rule, such as a requirement, or the definition of a term, have the `docs-reviewer` subagent read the documents that the change can affect. Find these documents without asking the user, even when they are every document of the repository:
  - for each document that the change adds, edits or deletes, the documents directly in its folder and directly in each folder above it up to the root, and those that link to it or give its path, found as the first bullet of this section says;
  - for a rule that the change adds, or changes so that a document that followed it may now break it, every document whose text the rule constrains, or, when a `git grep -i --untracked` search matches every text that can break the rule, such as a search for a word that the rule forbids, only the lines it matches, with their files and line numbers.

### Review findings

A finding must name the source of the change, rule, fact or required review check behind it and show the concrete error or unanswered case in the text. A suggestion without that evidence is not a finding; the reviewers list such suggestions after all findings, without a class. `docs-reviewer` and `behaviour-reviewer` give every finding one class and report findings in the class order below. Within each class, they report the most serious first.

- Breaks behaviour or a rule: the text gives behaviour that breaks a requirement, a scenario, a rule of its model or a source of the change under review, leaves out behaviour that they need, or adds behaviour that its model lacks; it states a wrong fact or contradicts another document; or it breaks a rule of the [conventions files](/AGENTS.md#conventions-files) in what it says or where it says it, such as a rule stated in two places or a link that the writing rules require and the text lacks.
- Two readings: a reader can take the text in more than one way, or cannot tell what it means, such as when a word can refer to two things or the text says two things that cannot both hold. Text that clearly allows more than one behaviour has one reading.
- Wording only: the text has one reading, that reading is right, and the text stands in the right place; it breaks a rule of the conventions files only in how it says it, such as a sentence longer than the minimum text needs, a list where a table would be shorter, or a link that leads to the right target in a path form that [link-paths.md](/docs/conventions/link-paths.md) does not allow.
- Outside the change: all of these hold:
  - the sentence, heading, table row or diagram line with the problem, or the place where missing text belongs, is as it was where the branch left `main` and has not moved;
  - the change neither causes nor worsens the problem, and nothing it adds or edits uses a rule, fact or term that the text with the problem states or defines;
  - neither a source of the change nor a rule or scenario of its model needs the fix, and no repository rule requires it in this change.

A finding that fits the class "Outside the change" takes it in place of the others. Of the rest, a finding about text whose meaning a reader cannot tell takes "Two readings", and one about text that a reader can take in more than one way takes "Breaks behaviour or a rule" when every plausible reading has a problem of that class, and "Two readings" otherwise. Any other finding that fits more than one class takes the first of them, and one that fits none takes "Breaks behaviour or a rule". A finding that asks whether a behaviour is intended takes the class it would have if the behaviour is not intended.

### Ending a review

This subsection says how each review that [Documents](#documents) requires ends: of the text of a document, which `docs-reviewer` and, for a specification edit that changes behaviour, `behaviour-reviewer` read in one review; of a behaviour model; and of the documents that a change can affect. A run of a review is a run of each reviewer that the review requires, with what Documents says to give it. A fix made in a review starts no other review. Ask the user, not Codex, about each finding that the [Decisions section](/docs/conventions/workflow.md#decisions) of the workflow sends to the user. Before you act on the findings of a run, check that each finding of the class "Outside the change" meets all its conditions, leave it out of the change and name it in your report as work for a later task.

A fix changes the meaning when it adds, removes or changes a rule, a requirement, a scenario, a state, an outcome, a fact or the definition of a term, moves one of them to another requirement, section or document, settles which of two readings holds, or makes the text rely on a document or section that it did not rely on, as the [writing rules](/docs/conventions/writing.md) define relying. Any other fix only rewords, such as adding a link to a section that the text already relies on.

- After the first run, weigh its findings and fix the text, the most serious first. When no fix changes the meaning, the review ends.
- Otherwise, give the files that the fixes touched to a second run. When it gives no finding other than "Outside the change", the review ends. No reviewer runs a third time in one review, apart from the light run below.
- Otherwise, weigh its findings, fix the text as after the first run and call Codex with the [`codex` skill](/.claude/skills/codex/SKILL.md). Give it the whole task, not only the diff: the sources of the change, for a specification edit its model and state tables, the text, the findings of both runs, what you and the user decided on each and where you got stuck. Ask Codex how it would make the change itself, whether the fixes made after the second run are right, and for one decision and its fix for each finding that you left undecided and that the Decisions section does not send to the user, and each place that a reader can take in more than one way.
- Make the fixes of Codex's answer and give them, with the parts of the text that they affect, to a light run, which gets no other part of the text. Make only the fixes of its findings that reword.
- When a fix of Codex's answer does not fit the rest of the text or the model, as you find or as the light run shows, tell the user what does not fit and that the order of work in these rules may need reconsidering, and stop.
- With your conclusions, name for each file in one line the fixes that you made to it since a reviewer or Codex last read it.

## Code

- During implementation, run the typechecks and the tests that run in Node of the packages the change touches, as the [testing rules](/docs/conventions/tests.md) tell them from the tests that run in a browser.
- Before reporting a change as done, run them also for the packages that depend on those, and run the browser tests of the affected requirements, as the next bullet defines them. The [documents on how to work](/docs/conventions/folder-docs.md#agentsmd) in the [project](/docs/glossary.md#project) that holds the packages give the commands, and [checks.md](/.github/docs/checks.md) says which browser tests CI runs.
- Before reporting a change as done, check each affected requirement against the code and its tests. Affected requirements are those the branch changes in `docs/specs/` since it left `main`, those that link to a specification file the branch changes, and, for the innermost project or [module](/docs/glossary.md#module) whose code includes a changed file, those of its own [specification](/docs/conventions/specs.md) that the changed code carries out and those of other specifications that link to a file of it. `git grep -i --untracked` in `*/docs/specs/*` finds the requirements that link there by the name of each changed specification file and of each folder of each such project or module; keep the matches whose link leads there.
- After a check of this section passes, repeat it only after a change that can affect its result or new evidence of a problem.

## Codex check

Before you first show the user a change for the approval that [Pull requests](/docs/conventions/workflow.md#pull-requests) asks for, after the other checks of these rules, call Codex once, on the whole change, with the [`codex` skill](/.claude/skills/codex/SKILL.md). Give it every change since the branch left `main`, uncommitted and untracked files included, and the agreed points in the user's request and the task's outline, with the piece named when the task has several. Ask whether the change weakens or breaks an agreed point or what already works, and whether a decision goes against common sense, such as a wait without an end, with arguments for and against each finding. Choose what to do with each finding by those arguments yourself or have a new subagent, which has not seen the discussion, choose, and ask the user only about a finding that the Decisions section sends to the user. Fixes of its findings start no other review and no second Codex check. When Codex cannot run, here or in [Ending a review](#ending-a-review), replace it with no other check and go no further: fix what keeps it from running, apart from the setup that the `codex` skill leaves to the user, or stop at once and give control back to the user.
