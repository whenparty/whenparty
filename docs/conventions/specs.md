# Specifications

A [project](/docs/glossary.md#project) or [module](/docs/glossary.md#module) needs a specification when the `AGENTS.md` of a project that contains it says so. Otherwise a specification is optional. These rules cover every specification, its `docs/PLANNED.md` and the part of a project's `AGENTS.md` that says so.

A project or module with a specification keeps it in its own `docs/specs/` folder, one file per topic. A specification describes observable behaviour: what people, other projects and other modules can see the code do or rely on. A rule belongs to the specification of the innermost project or module that holds the code carrying it out, and to none if that has none. A rule that holds only when several modules work together belongs to the specification of their nearest common project or module; when that has none, the user decides whether it gets one. Internal state and implementation choices, such as function names, message formats and library settings, are not part of a specification, even when another project of the repository relies on them. They are part of it only when a person or a program whose code is not in the repository relies on them, such as an address that people open, a timeout that nginx or Cloudflare applies, or the format of TURN credentials that coturn checks.

## Content

- The specification on `main` describes the behaviour implemented on `main`. On a branch, it also describes the part of a change that the branch implements, including requirements its code does not meet yet. When behaviour changes, rewrite or delete the requirement in place.
- Number each specification file and give it a short topic name, such as `1-match.md`. A requirement's ID is the file number and the requirement's number in that file, such as `1-3`. A new requirement takes the number after the last one in its file; before a branch reaches `main`, it may renumber the requirements it added. IDs are local to one specification. To refer to a requirement in another file, of this specification or another, link to that file with the requirement's ID as the link text, such as `[3-3](3-match.md)`.
- Splitting or regrouping the files of a specification is a reformat, made in a commit of its own that changes no behaviour. It numbers the requirements of every file involved from 1 in order and changes no requirement's text except its references and links. A new file takes the number after the last file, a file may get a new topic name, a file left without requirements is deleted, and the other files keep their numbers. A requirement test checks one file, as the [testing rules](/docs/conventions/tests.md) say, so requirements that one test checks stay in one file. The same commit moves their tests to the test file named after their new specification file and updates every other reference to the renumbered requirements and renamed files, including test names.
- A requirement relies on another when it uses a value, term, table or rule that only the other states. Using a term that its own specification defines is not relying on its definition. A requirement that a change adds or rewrites, or whose file a reformat involves, refers to each requirement in another file that it relies on. A requirement's links to documents outside specifications follow the [writing rules](/docs/conventions/writing.md). Adding, removing or retargeting links in a requirement without changing its other words does not rewrite it. A requirement links to no other specification that relies on its own, directly or through others.
- State each rule precisely enough that its boundaries follow from it, in the terms of the domain. A requirement that a change adds or rewrites also follows the rest of this bullet. When someone acts, it names who, such as the host or the page. When the rule holds only under a condition, it opens with the condition, such as "When a player leaves". It says what happens to invalid input and, for several conditions, whether all must hold or one is enough. It gives amounts and times as numbers with units. A list in it names every member, or says with "such as" that it gives only examples. A rule that can change on its own gets a requirement of its own.
- A table or diagram in a specification sits inside one requirement, indented under its list item, and is part of it. Other requirements refer to it by that requirement's ID.

## Planned changes

- The `docs/PLANNED.md` of a project or module with a specification lists accepted changes that are not in the specification yet and that any later task may take up; it exists only while it has any and does not describe the system. When work on an item starts, move it into the specification, as a changed or new requirement, and delete it from `docs/PLANNED.md`. An item may name the requirement it would change. Delete cancelled items. The pieces and agreed points of an outline, which the [workflow](/docs/conventions/workflow.md#cutting-a-task-into-pieces) describes, are not items.
