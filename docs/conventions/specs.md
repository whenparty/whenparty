# Specifications

A [project](/docs/glossary.md#project) or [module](/docs/glossary.md#module) needs a specification when the `AGENTS.md` of a project that contains it says so. Otherwise a specification is optional. These rules apply to every specification, to its `docs/PLANNED.md` and to the list of relying requirements in its `AGENTS.md`.

A project or module with a specification keeps it in its own `docs/specs/` folder, one file per topic, and its other documentation in `docs/`. A project's specification describes its observable behaviour: what its users, people or other projects, can see it do or rely on. A module's specification describes only its [boundary](/docs/glossary.md#module). What other projects rely on belongs to the specification of the project that holds the module. Internal state and implementation choices are not part of a specification.

## Content

- The specification on `main` describes the behaviour implemented on `main`. On a branch, it also describes the part of a change that the branch implements, including requirements its code does not meet yet. When behaviour changes, rewrite or delete the requirement in place.
- Number each specification file and give it a short topic name, such as `1-match.md`. A requirement's ID is the file number and the requirement's number in that file, such as `1-3`. A new requirement takes the number after the last one in its file; before a branch reaches `main`, it may renumber the requirements it added. IDs are local to one specification. To refer to a requirement in another file, of this specification or another, link to that file.
- Splitting or regrouping the files of a specification is a reformat, made in a commit of its own that changes no behaviour. It numbers the requirements of every file involved from 1 in order and changes no requirement's text except its references. A new file takes the number after the last file, a file may get a new topic name, a file left without requirements is deleted, and the other files keep their numbers. Requirements that one test checks stay in one file, because a requirement test checks one file, as the [testing rules](/docs/conventions/tests.md) say. The same commit moves their tests to the test file named after their new specification file and updates every other reference to the renumbered requirements and renamed files anywhere in the repository, including test names.
- The `AGENTS.md` of a project or module lists the requirements of other specifications that rely on its behaviour.
- State each rule precisely enough that its boundaries follow from it, in the terms of the domain.

## Planned changes

- The `docs/PLANNED.md` of a project or module with a specification lists accepted changes that are not in the specification yet and that any later task may take up. It does not describe the system. When work on an item starts, move it into the specification, as a change to an existing requirement or as a new one, and delete it from `docs/PLANNED.md`. Only finished work reaches `main`. A branch writes its own work there only when it reaches `main` with part of its specification edit not done: that part moves to `docs/PLANNED.md` as items without IDs of their own, its tests and unfinished code are removed, and the specification keeps only what the code does. The user approves what moves there. An item may name the requirement it would change. Delete cancelled items.
