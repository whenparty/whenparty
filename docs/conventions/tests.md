# Tests

Test the requirements in the [specification](/docs/conventions/specs.md) of a project or module and specific failure risks of its implementation. Every requirement needs a test. Requirement tests check the boundaries of each rule with concrete values, and every row or transition of a requirement's table or diagram. Keep the smallest test set that protects them. Name a requirement test file after its specification file, such as `1-match.test.ts` for `1-match.md`. A requirement test checks requirements of one specification file. Its name starts with the full IDs of the requirements it checks, such as `1-3`, not of those it relies on for setup. Name a failure-risk test file after the code it protects; its tests carry no IDs. Seeded fuzz tests are useful when event combinations expose a separate risk. Extend an existing scenario when it already protects that behaviour. Remove duplicate checks and tests that protect neither a requirement nor a specific risk; do not target line coverage or a test count.

A thing that the requirements of a specification file describe and that has states, such as a connection or a match, gets a state table, so that no pair of a state and an event is missed. A state is a condition in which the thing reacts to at least one event differently than in its other states. The table is a data file in the language of the tests, among the requirement tests of that file and named after it, such as `2-connection.states.ts`. When the requirements of several files describe one thing, each file gets a table for the states that its requirements tell apart. A table's states are those, and any state the code turns out to need. Its events are everything that can happen in a state: each call of the public interface, each input from another party, each time limit that passes, each limit that is reached and each failure of something the thing depends on, such as the network, a server or code that it calls. It has a cell for every pair of a state and an event, and where the language can check that, its type requires every cell. A cell holds the outcome as values that a test checks and the full IDs of the requirements that state it or that it follows from, or says that the pair cannot happen and why. Each cell that has an outcome has a test of its own, whose name starts with the cell's requirement IDs; it is also the test of the matching transition of a requirement's diagram. When requirements hold in any order of events, such as that a connection closes once, a seeded fuzz test sends the table's events in random orders and checks them; its name starts with their IDs. The [workflow](/docs/conventions/workflow-specs.md) says when the table is written and what to do when the requirements leave a cell open or the code needs a new state.

Requirement tests verify behaviour through the public interface of the project or module, whichever files implement it. A test of internal code needs a specific risk that requirement tests do not cover. Tests of one specification do not re-verify rules that another specification states.

Use unit tests by default. Add non-browser [integration tests](/docs/glossary.md#integration-test) only when unit tests cannot verify a required interaction, and browser integration tests only when a non-browser one cannot, such as a connection through the TURN relay. A browser integration test file ends in `.browser.test.ts`, such as `1-match.browser.test.ts`, and otherwise follows the naming rules above.

Use controlled time for deadlines. Do not wait through application timeouts. Bound real network waits.
