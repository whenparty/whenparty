# Workflow: specifications and code

These rules say how specifications and code change in a [project](/docs/glossary.md#project) or [module](/docs/glossary.md#module). [workflow.md](/docs/conventions/workflow.md) says how to work on any change, and [workflow-checks.md](/docs/conventions/workflow-checks.md) what to check along the way.

- In a project or module with a specification, every code change follows the [testing rules](/docs/conventions/tests.md). First decide whether the change alters the behaviour the specification describes. If it does, it takes the steps of [Behaviour changes](#behaviour-changes). If it does not, as with refactoring or a fix that matches an existing requirement, the specification stays as it is. The exception is splitting or regrouping its files, which the [specification rules](/docs/conventions/specs.md) describe: it changes the specification without altering behaviour. The user approves it first.
- If the task changes code of a [project](/docs/glossary.md#project) or [module](/docs/glossary.md#module) that needs a [specification](/docs/conventions/specs.md) and has none, stop. Say that these rules expect one, and ask whether to set it up first or to work without it.
- The specification edit and the code reach `main` together, in one pull request. Only finished work reaches `main`. A branch writes its own work into [`docs/PLANNED.md`](/docs/conventions/specs.md#planned-changes) only when it reaches `main` with part of its specification edit not done: that part moves there as items without IDs of their own, its tests and unfinished code are removed, and the specification keeps only what the code does. The user approves what moves there.
- When a test would have to check requirements of several specification files, a requirement about how they fit together is missing. Propose it to the user.
- During implementation, change the specification only as approved. When a requirement turns out wrong or incomplete, stop and ask.

## Behaviour changes

A behaviour change, a new specification included, takes these steps in order. Steps 1 and 2 apply only when the specification edit adds, changes or removes requirements of a thing that needs a state table, as the testing rules say, or changes the behaviour of more than one project or module.

1. Write a behaviour model of each project or module that the change affects: a state diagram of each thing with states, the parties and how each of them can fail, and scenarios, each with its expected outcome. The model is a working document of the change and is not committed.
2. Have the model reviewed, as [workflow-checks.md](/docs/conventions/workflow-checks.md#documents) says. The user decides each finding that needs the user's decision, such as accepting a weaker guarantee. Then the user reads the whole model and approves it.
3. Write the specification edit in the specification files of the branch, from the approved model when there is one. Claude Code asks for confirmation before editing these files, as [configuration.md](/.claude/docs/configuration.md) describes. When the edit adds, changes or removes requirements of a thing that needs a state table, build or update the table from the edited specification; the table is not implementation. A thing that has no table yet gets one with such an edit, not with a change that leaves its requirements as they are. A cell is open when the requirements neither state its outcome nor imply it, or allow more than one outcome. Add a requirement to the edit for each open cell, and none for a cell whose outcome follows from the requirements the specification has. When there is a model, run every scenario of it through the edited text and its tables: the expected outcome must follow from them.
4. Have the edit and its tables reviewed, as workflow-checks.md says. When a reviewer suggests behaviour that the model and the sources of the change lack, ask the user instead of adding it to the edit. When the user accepts it, add it to the model, when there is one, and then to the edit.
5. Propose the edit and its tables. The user approves them before implementation.
6. Write the tests of the edited requirements and of their tables, then the code that passes them. The code adds no state that a table lacks. When it needs one, pause the implementation, add the state to the table, fill its cells from the specification and give the table to a new run of the [`behaviour-reviewer` subagent](/.claude/agents/behaviour-reviewer.md). Continue when no cell is open and the reviewer's findings change no requirement; otherwise a requirement is incomplete, as the last rule of the list above says.
