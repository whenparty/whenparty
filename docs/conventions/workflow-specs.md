# Workflow: specifications and code

These rules say how specifications and code change in a [project](/docs/glossary.md#project) or [module](/docs/glossary.md#module). [workflow.md](/docs/conventions/workflow.md) says how to work on any change, and [workflow-checks.md](/docs/conventions/workflow-checks.md) what to check along the way.

- In a project or module with a specification, every code change follows the [testing rules](/docs/conventions/tests.md). First decide whether the change alters the behaviour the specification describes. If it does, it starts with a specification edit, as described below. If it does not, as with refactoring or a fix that matches an existing requirement, the specification stays as it is. The exception is splitting or regrouping its files, which the [specification rules](/docs/conventions/specs.md) describe: it changes the specification without altering behaviour. The user approves it first; for a document over the word limit, the user's answer to the proposal that the [Decisions section](/docs/conventions/workflow.md#decisions) of the workflow requires is that approval.
- If the task changes code of a [project](/docs/glossary.md#project) or [module](/docs/glossary.md#module) that needs a [specification](/docs/conventions/specs.md) and has none, stop. Say that these rules expect one, and ask whether to set it up first or to work without it.
- A behaviour change starts with a specification edit that the user approves before implementation. Claude Code asks for confirmation before editing specification files, as [configuration.md](/.claude/docs/configuration.md) describes.
- The specification edit and the code reach `main` together, in one pull request or one direct push, from a branch in both cases. When only part of the work is done, the specification rules say what reaches `main` ([planned changes](/docs/conventions/specs.md#planned-changes)).
- A change that adds, changes or removes a reliance on a requirement of another project or module updates the specification and that project's or module's list of relying requirements together.
- When a test would have to check requirements of several specification files, a requirement about how they fit together is missing. Propose it to the user.
- During implementation, change the specification only as approved. When a requirement turns out wrong or incomplete, stop and ask.
